# gpic

Генератор обоев для рабочего стола. Одна команда без аргументов кладёт в текущий
каталог свежую картинку под разрешение твоего монитора.

Всё считается **локально**: картинку рисует FLUX.1-schnell через
[stable-diffusion.cpp](https://github.com/leejet/stable-diffusion.cpp), а описание
для неё придумывает Qwen2.5-1.5B через
[llama.cpp](https://github.com/ggml-org/llama.cpp). Оба движка на Vulkan.

Ни ключей, ни аккаунтов, ни лимитов, ни прокси. Картинка рождается сразу в нужном
разрешении — она не растягивается из чего-то меньшего.

## Установка

```sh
git clone https://github.com/hr82al/gpic
cd gpic
./setup.sh
```

`setup.sh` делает всё сам: доставляет недостающие системные пакеты, собирает
движок, качает веса и ставит лаунчер в `~/.local/bin/gpic`. Скрипт идемпотентен —
если загрузка оборвалась, запусти его снова, он продолжит с места остановки.

В конце проводится контрольная генерация с замером времени, чтобы ты сразу знал,
чего ждать от своего железа.

Если GitHub или Hugging Face медленно отдают, запусти через прокси — `curl` и
`git` читают стандартные переменные окружения:

```sh
HTTPS_PROXY=http://127.0.0.1:8888 ./setup.sh
```

## Использование

```sh
gpic                                        # картинка под разрешение экрана
gpic --fast                                 # минута вместо шести с половиной
gpic --random                               # всегда необычный сюжет
gpic -r 2560x1440                           # своё разрешение
gpic -p "winter forest at sunrise"          # свой промпт
gpic -s 319553386                           # повторить конкретную картинку
gpic wall.png                               # своё имя файла
```

`--fast` рисует моделью SDXL-Turbo вместо FLUX: **20 секунд вместо шести с
половиной минут**. Картинка создаётся в четверти целевого размера и
увеличивается нейросетевым ESRGAN — не растягивается, а дорисовывается.

Так сделано вынужденно: SDXL-Turbo обучен на 512×512, и если просить у него
сразу разрешение экрана, он достраивает композицию повторением — сросшиеся
фигуры, лишние руки, два горизонта. На пейзаже это можно не заметить, на
портрете видно сразу.

Без `-p` описание придумывает маленькая языковая модель (Qwen2.5-1.5B через
`llama.cpp`), а не список слов. Перечислять сюжеты руками бессмысленно: сколько
ни пиши, получается конечный список, который приедается. Модель же внутри темы
выдумывает без потолка.

Работает в двух режимах:

| Режим | Доля | Что просим |
|---|---|---|
| Обычный | 70% | описание по случайной теме из сорока областей — от глубоководной жизни до промышленных интерьеров |
| Творческий | 30% | необычный угол: «две несвязанные вещи в одной сцене», «микроскопическое как пейзаж», «архитектура, растущая как растение» |

Творческий режим держится на `min-p`, а не на голой температуре: он отсекает
маловероятные токены, поэтому описание остаётся связным там, где одна температура
уже давала бы бессвязицу.

Если `llama.cpp` не собрался, `gpic` работает по запасному списку из дюжины
описаний — однообразно, но работает.

Флаг `--random` включает творческий режим принудительно, а не в 30% случаев.

Seed внутри каждого описания множит разнообразие практически без предела.

Без имени файла получается `gpic-ГГГГММДД-ЧЧММСС.png` в текущем каталоге.
Использованный seed печатается — по нему картинку можно воспроизвести побайтово.

Промпты стоит писать по-английски: FLUX обучался на английских подписях и
понимает их точнее. Русский тоже примет — T5 многоязычный, — но следование
описанию будет слабее.

## Чего ждать по времени и памяти

Измерено на Ryzen 7 255 со встроенной Radeon 780M (4 ГБ VRAM + 13.9 ГБ GTT):

| Режим | Разрешение | Время | Пик памяти |
|---|---|---|---|
| FLUX, обычный | 1920×1200 | **6 мин 25 с** | 17.4 ГБ |
| SDXL-Turbo, `--fast` | 1920×1200 | **20 с** | ~7 ГБ |

Время определяется вычислениями, а не перекачкой весов: прогнать 8 ГБ через
шину стоит доли секунды, тогда как шаг занимает 84. Поэтому оно растёт как
произведение числа параметров на число токенов, и вес в Q8 идёт не медленнее
Q5 — только требует больше памяти.

Процессор при генерации почти не работает: за шесть с половиной минут он
тратит меньше минуты, вся нагрузка на видеокарте. Машина остаётся отзывчивой.

## Что где лежит

| Путь | Содержимое | В git |
|---|---|---|
| `gpic.py` | вся логика | да |
| `setup.sh` | развёртывание | да |
| `build/` | исходники и бинарники обоих движков | нет |
| `models/` | веса FLUX, SDXL, ESRGAN и языковой модели, около 32 ГБ | нет |

Тяжёлое намеренно не попадает в репозиторий — в нём только текстовые файлы.

## Требования

- Linux, Python 3 (только стандартная библиотека, `pip install` не нужен)
- около 40 ГБ свободного места
- 24 ГБ оперативной памяти (пик 17.4 ГБ); видеокарта с Vulkan желательна, но не обязательна:
  если сборка с Vulkan не удастся, `setup.sh` пересоберёт движок в режиме CPU

## Удаление

```sh
rm -rf build models ~/.local/bin/gpic
```

## Почему именно эти флаги движка

`gpic.py` запускает `sd` с тремя неочевидными флагами. Каждый из них не
оптимизация, а условие работоспособности — это выяснилось замерами, и все три
подробно прокомментированы в коде.

| Флаг | Без него |
|---|---|
| `--diffusion-fa` | буфер внимания не влезает в лимит Vulkan, движок сваливается на медленный путь: **337 с на шаг вместо 88**, пик памяти 26.4 ГБ вместо 14.9 |
| `--vae-tiling` | декодирование картинки размером с экран требует буфера больше 4 ГБ VRAM, драйвер теряет устройство (`device lost on Vulkan0`) и результат гибнет **после** того, как все шаги отработали |
| `--params-backend te=disk` | текстовые энкодеры на 3.4 ГБ висят в видеопамяти до конца, хотя нужны только на первой стадии |

Вместе они дают пик 17.4 ГБ вместо 27 — то есть разницу между «работает при
запущенном браузере» и «система уходит в своп».

Отдельно: движок выравнивает размеры (SDXL до кратного 64, FLUX до 16), поэтому
`gpic.py` запрашивает размер с округлением вверх и сам подрезает результат до
точного. Разбор PNG написан на стандартной библиотеке — тянуть Pillow ради
обрезки нескольких строк пикселей несоразмерно.

Веса выбираются автоматически: программа берёт первый **докачанный** вес из
списка предпочтений (Q8, иначе Q5) и печатает свой выбор при запуске. Проверка
по размеру нужна потому, что на оборванном файле движок выдаёт невнятное
`read tensor data failed`.
